# Desired End State

## Product

Avery can open a protected Agentic Inbox web application and manage the `avery@unixgreybeard.org` mailbox through a usable browser interface. The application displays folders, threads, HTML email, attachments, search results, compose/reply/forward controls, and the AI agent side panel.

## Cloudflare deployment

- A production Cloudflare Worker named for Agentic Inbox is deployed from the repository.
- The Worker serves the compiled React/React Router application and Hono API.
- Durable Object classes and SQLite migrations are deployed and operational for mailbox isolation and agent state.
- R2 is bound for attachment persistence and retrieval.
- Workers AI is bound for the configured email-agent model.
- Email Service's `send_email` binding is operational for outbound mail.
- Email Routing forwards the intended inbound domain/mailbox traffic to this Worker.
- The custom domain/route is configured for the intended Cloudflare zone.
- Cloudflare Access protects production, with correct `POLICY_AUD` and `TEAM_DOMAIN` secrets stored as Worker secrets and never in Git.

## Email behavior

- Inbound email to `avery@unixgreybeard.org` reaches the Worker through the approved routing configuration.
- The message is parsed, stored in the correct mailbox Durable Object SQLite database, and appears in the UI.
- Attachments are stored in R2 and can be listed/downloaded through authorized application routes.
- The AI agent can read and search messages and create drafts.
- Agent-created drafts require explicit user confirmation before sending.
- Approved outbound replies are sent through Cloudflare Email Service with correct sender, recipient, threading, and expected delivery behavior.
- Google Workspace remains the intended primary mail ecosystem unless later specifications define a different routing model.

## Verification

The desired end state is supported by evidence, not assumptions:

- `npm run build` succeeds.
- `npm run typecheck` succeeds.
- Focused unit/integration checks succeed.
- Browser smoke tests connect to the local Chrome debugger when testing locally and verify the important UI paths.
- Wrangler deployment succeeds and returns a real deployment/version identifier.
- Authenticated production UI loads.
- Unauthenticated production access fails closed.
- Controlled inbound email is visible in the intended mailbox.
- Controlled attachment and outbound-send tests pass.
- Agent read/search/draft/confirmation/send behavior is verified.
- No credentials or private message contents appear in committed files or diagnostic output.

## Operations and rollback

- Deployment commands are documented and repeatable.
- Resource names, binding names, migration tags, Access configuration, and required manual Google Workspace/Cloudflare dashboard steps are recorded.
- A previous known-good Worker version can be identified and restored through Wrangler if a deployment must be rolled back.
- The repository has a clear distinction between source configuration, local specifications, secrets, and generated artifacts.

## Final handoff artifact

A final project report in the repository records:

- What was built and changed.
- What was deployed and where.
- Cloudflare Worker/resource identifiers.
- Verification commands and actual outcomes.
- Email routing and Google Workspace prerequisites.
- Required secrets by name only, never by value.
- Remaining limitations and follow-up work.
- Rollback procedure.

## Work backwards from here

1. Define and protect the production inputs.
2. Make the local build and tests green.
3. Make the binding configuration match the source architecture.
4. Provision and verify Cloudflare resources.
5. Deploy behind Access.
6. Prove inbound, attachment, agent, and outbound flows.
7. Harden, document, and hand off.

Do not treat a successful JavaScript build or Worker upload alone as completion. Completion requires the protected, end-to-end email workflow above.
