# Project Objectives

## Primary objective

Build, test, configure, and deploy the `cloudflare/agentic-inbox` application as a working Cloudflare Workers email application for Avery's primary Google Workspace mailbox, `avery@unixgreybeard.org`.

## Minimum viable outcome

A compiled and deployed Agentic Inbox installation with:

- A Cloudflare Worker serving the web application and API.
- Durable Objects with SQLite storage for isolated mailboxes.
- An R2 bucket for email attachments.
- Workers AI available to the email agent.
- Cloudflare Email Routing configured to deliver inbound mail to the Worker.
- Cloudflare Email Service / `send_email` configured for outbound mail.
- Cloudflare Access enforced in production with `POLICY_AUD` and `TEAM_DOMAIN` secrets.
- The primary mailbox configured for `avery@unixgreybeard.org`.
- A verified end-to-end path for receiving, displaying, agent-processing, drafting, and sending email, subject to the user's final specifications and provider permissions.

## Quality objectives

- Keep secrets out of Git, logs, generated source, and committed configuration.
- Prefer the repository's intended Cloudflare primitives and documented setup over ad-hoc infrastructure.
- Preserve mailbox isolation and the production Access trust boundary.
- Validate the browser experience and agent interactions, not only TypeScript compilation.
- Make deployment reproducible with documented commands and environment requirements.
- Record actual deployment identifiers, URLs, bindings, tests, and remaining manual dashboard steps in a final project report.

## Important constraints

- `.env` contains secrets and must not be printed, read into conversation, committed, or exposed in reports.
- `.env.local` is expected to receive additional non-secret specifications later; do not overwrite it or invent missing values.
- The project may require Cloudflare dashboard actions that cannot safely be guessed, especially Email Routing, Email Service, Access, and domain authorization.
- Deployment is a consequential external side effect. Execute it only after local build/tests and configuration review are complete, and report exactly what was deployed.

## Success definition

The project is successful when the deployed Worker is reachable behind the intended Access policy, its Worker bindings are healthy, the UI loads, a mailbox for `avery@unixgreybeard.org` can be used, and representative inbound/outbound email and AI-agent flows have been verified with evidence.
